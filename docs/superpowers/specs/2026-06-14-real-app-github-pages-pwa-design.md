# Real App Launch: GitHub Pages PWA Design

Date: 2026-06-14

## Decision

Launch the first real version of Museum of Seeing as a GitHub Pages PWA.

This is Route A from the product discussion: keep the app static and lightweight, but make it installable, trustworthy, mobile-ready, and stable enough for daily use. This route intentionally avoids accounts, database work, payments, native app packaging, and a parent analytics dashboard in the first launch.

## Product Goal

Museum of Seeing should feel like a real daily aesthetic-learning app for children ages 7-9, not a prototype page.

A child should be able to open the app on a phone, see today's museum artwork, complete a short looking-and-making ritual, finish on a clear completion screen, and return later to see their visual history. A parent should be able to understand what the app is, where the artwork comes from, and what data is stored.

## First Launch Scope

Included:

- GitHub Pages production deployment.
- Installable PWA metadata and icons.
- Service worker for app shell caching and graceful offline opening.
- Mobile-first home screen that presents today's mission instead of prototype instructions.
- Daily mission loading from `museum-library.json`, falling back to `daily-missions.json`, then built-in missions.
- Ten-day museum material library generated by the existing Node script.
- GitHub Actions daily update that commits both `daily-missions.json` and `museum-library.json`.
- Parent page with concrete content: educational purpose, source transparency, privacy, local storage, and age guidance.
- Basic SEO/social metadata so the app link looks intentional when shared.
- Local-only check-in history and completion state.
- English, Simplified Chinese, and French language support.

Excluded:

- User accounts or child profiles.
- Cross-device sync.
- Payments or subscriptions.
- Native iOS/Android packaging.
- Push notifications.
- AI chat or free-form generation.
- Server-side database or admin CMS.

## User Experience

The first screen should stop saying "prototype" as the main product identity. It should behave like a real app home:

1. Show the app name and a short product promise.
2. Show today's artwork or today's mission status.
3. Provide one obvious primary action to start or continue the daily mission.
4. Surface streak/history lightly without turning the product into a points game.
5. Keep Parents and language controls visible but secondary.

The daily loop remains:

1. Home.
2. Daily artwork mission.
3. Color/observation selection.
4. Atelier creation.
5. Completion screen.
6. Seeing history.

The completion screen is important. It should make the day feel finished, show the artwork and selected palette, and invite returning tomorrow.

## Architecture

Keep the current static architecture:

- `index.html`: screen markup, PWA metadata, SEO/social metadata.
- `styles.css`: mobile-first product visual system.
- `main.js`: local app state, screen rendering, mission loading, check-ins, language, service worker registration.
- `museum-library.json`: rolling ten-day material library.
- `daily-missions.json`: today's extracted mission.
- `scripts/update-daily-missions.mjs`: content generation.
- `.github/workflows/update-daily-missions.yml`: scheduled daily update.
- `manifest.webmanifest` or `manifest.json`: install metadata.
- `service-worker.js`: app shell and content cache.
- `assets/icons/`: install icons.

No backend is required for this launch. Local browser storage remains the persistence layer.

## Data Flow

At startup:

1. Load built-in missions immediately as fallback.
2. If online and not opened from `file://`, fetch `museum-library.json` with no-store cache busting.
3. Select the entry matching `todayKey()`.
4. If no matching library entry exists, use the first library entry.
5. If library loading fails, fetch `daily-missions.json`.
6. If all remote loading fails, keep the built-in mission.

Daily update:

1. GitHub Actions runs `scripts/update-daily-missions.mjs` daily.
2. The script generates a ten-day rolling library starting from the current date.
3. The script writes both `museum-library.json` and `daily-missions.json`.
4. The workflow commits both files.
5. GitHub Pages deploys the updated static site.

## PWA Behavior

The app should be installable on mobile and desktop browsers that support PWAs.

Manifest requirements:

- App name and short name.
- Description.
- Start URL and scope compatible with GitHub Pages subpath deployment.
- Standalone display.
- Theme and background colors matching the app.
- 192 and 512 icons.

Service worker requirements:

- Cache app shell files.
- Cache manifest and icons.
- Use network-first for `museum-library.json` and `daily-missions.json`.
- Fall back to cached content when offline.
- Do not block the app if service worker registration fails.

## Parent Trust

The Parents screen must be functional, not decorative.

It should explain:

- The learning goal: looking, color sensitivity, visual language, and museum familiarity.
- Artwork sources and public-domain/open collection usage.
- That no account is required.
- That history is stored locally on the device.
- That clearing browser storage clears the child's local diary.
- That parents should treat the app as a short shared ritual, not a performance test.

## Error Handling

- If daily content fails, show built-in fallback content.
- If artwork image loading fails, preserve layout and show title/credit.
- If local storage fails, run in session-only mode without crashing.
- If service worker registration fails, keep the online app working.
- If GitHub Actions fails, previous deployed data remains available.

## Testing

Minimum verification before calling the launch ready:

- JSON validation for `museum-library.json` and `daily-missions.json`.
- Ten-day library check: 10 entries, first date is today, each entry has artwork URL and choices.
- Local HTTP smoke test for page load.
- Confirm the page requests `museum-library.json`.
- Confirm manifest and service worker are reachable over HTTP.
- Mobile viewport check for home and daily mission flow.
- GitHub Pages deployment check after push.

## Success Criteria

The launch is successful when:

- The public URL opens on a phone.
- The app can be added to the home screen.
- The first screen reads like a product, not a prototype note.
- A child can complete today's mission without adult explanation.
- A parent can understand privacy and source material from the Parents page.
- The ten-day library updates daily through GitHub Actions.
- The app still opens with fallback content when remote daily content is unavailable.
